- type: paragraph
  text: |-
    A computer will quite happily keep track of a rule that nobody playing the game understands. I appreciate that when it’s doing arithmetic for me. It becomes a problem when I’m trying to practise showing a player enough to make a decision. Taking the computer away gave me a surprisingly good exercise.
- type: paragraph
  text: |-
    With paper on the table, somebody has to remember the rule, point to the thing that changed or stop the game to work it out. As the designer I have to decide where that work belongs. That’s the reason I chose the constraint.
- type: heading-2
  text: "Find the crutch first"
- type: paragraph
  text: |-
    In digital development, I can rely on automation to track complex states. I can add interface text to explain an unclear rule. I can use a powerful engine and a lot of scripting to make an awkward interaction technically functional.
- type: paragraph
  text: |-
    Those are useful tools [SIDENOTE]and I use them too[/SIDENOTE]. They become a problem only when I rely on them instead of understanding the design underneath. If I want to improve my ability to communicate rules, I might deliberately choose an exercise with no tooltips or automatic state changes.
- type: paragraph
  text: |-
    Say I want to practise encounter pacing next. I could give myself the same few enemies for a whole level. Now I have to decide when the player sees them, where there’s room to move, and how long the player gets to recover. If every encounter still feels the same, I know where to spend the next afternoon.
- type: paragraph
  text: |-
    The key is choosing the constraint because of the skill it exposes. 'Make it harder' is not a learning objective. 'Remove the tool that currently hides this design problem' is much more useful.
- type: heading-2
  text: "A good constraint changes the questions"
- type: paragraph
  text: |-
    Suppose I want to create a small exploration game. With unlimited scope, I can add more locations whenever the experience feels thin. If I restrict myself to one environment, that escape route disappears. I have to make the space interesting through reuse, changes over time, observation and player choices.
- type: paragraph
  text: |-
    Perhaps a path that was safe in daylight becomes useful for a different reason at night. Perhaps the player learns the environment well enough to notice a subtle change. The limited map pushes me to investigate how context changes the meaning of a familiar place.
- type: paragraph
  text: |-
    The constraint is valuable if it creates useful design problems. If it merely prevents me from testing the idea I care about, it is the wrong constraint.
- type: heading-2
  text: "Constraints can reveal the core interaction"
- type: paragraph
  text: |-
    One of the things I admire about playful, experimental game design is how much can emerge from a small set of understandable verbs. When the action feels good and the world responds, a designer can vary the context rather than constantly adding new controls.
- type: paragraph
  text: |-
    A deliberate control limit makes that philosophy concrete. Imagine a platforming prototype with only movement and jump. Without a complicated ability tree, I have to study acceleration, landing feedback, camera movement, obstacle shapes and the timing of risk.
- type: paragraph
  text: |-
    If the prototype isn't engaging, I learn something important. Perhaps the movement lacks responsiveness. Perhaps the obstacles don't demand interesting judgement. Adding a dash might genuinely help, but I want to know what problem the dash would solve before treating it as the default answer.
- type: paragraph
  text: |-
    Once I understand the basic experience, I can remove the restriction deliberately. A constraint should be a tool for finding clarity, not an ideology that forbids useful complexity forever.
- type: heading-2
  text: "What can I learn in a weekend?"
- type: paragraph
  text: |-
    **A weekend prototype.** I could spend those two days seeing how much of a game I can build. Or I could give someone the same action in three different situations and find out when they stop wanting to do it.
- type: paragraph
  text: |-
    The second version tells me what to prepare before Saturday and what to watch for when somebody plays. It also leaves me enough time to change something.
- type: heading-2
  text: "The constraint should eventually be questioned"
- type: paragraph
  text: |-
    I don't want the learning exercise to become a prison. After a round of testing, I ask whether the constraint is still exposing a useful weakness or has begun preventing progress.
- type: paragraph
  text: |-
    Imagine a narrative prototype that initially forbids dialogue text. That might teach me to communicate character intentions through animation, staging and environment. But if the final game depends on nuanced conversation, keeping the restriction forever could distort the project.
- type: paragraph
  text: |-
    A useful outcome might be a hybrid: keep the stronger nonverbal cues, then reintroduce concise dialogue where it adds depth. The constraint has done its job by changing my habits, not by becoming a permanent production rule.
- type: heading-2
  text: "The learning-project loop"
- type: paragraph
  text: |-
    The process I described in my NZGDC talk follows a simple route: pick a skill, find the crutch, choose a constraint, build small, find friction, reflect and transfer. I think of the final step as especially important.
- type: paragraph
  text: |-
    If I learn to make physical state visible in one exercise, where could that help a digital interface? If I learn to pace decisions with a tiny encounter, where might that apply to a larger quest? I don't want the lesson to stay trapped inside the project that created it.
- type: paragraph
  text: |-
    [BLOCK]I’d put the tool back as soon as I’d learned what I needed. I want the computer to do the arithmetic again. I also want to remember which result the player needed to see before choosing their next move.[/BLOCK]
